# UniSched-AI — Live Demonstration & Evaluation Guide

This guide provides a step-by-step script for demonstrating the **UniSched-AI** system during project evaluation, grading reviews, or viva examinations.

---

## 🏁 Step 0: Quick Startup

### Option A: Single-Command Production Demo (Recommended)
From the repository root:
```bash
# 1. Build the frontend production bundle (one-time)
npm --prefix frontend run build

# 2. Launch the FastAPI server
uvicorn api.main:app --port 8000
```
Open **`http://localhost:8000`** in your browser.
* Notice that FastAPI automatically serves the React SPA and API from a single port without needing a separate dev server.

### Option B: Concurrent Development Mode
* Terminal 1: `uvicorn api.main:app --reload --port 8000`
* Terminal 2: `cd frontend && npm run dev`
* Open: **`http://localhost:5173`**

## 📋 Step-by-Step Demo Script

### 1. Dashboard & Theoretical Concepts (The "Why")
1. Open the home page at **`/`**.
2. **Key Talking Points:**
   * Point out the **No-Machine-Learning statement**: Emphasize that the solver uses 100% classical symbolic AI and discrete CSP search—no neural network hallucinations.
   * Expand the **FAI Concepts Panel**:
     * Show the **PEAS breakdown** (Performance measure, Environment, Actuators, Sensors).
     * Show the **6 Environment Properties** (Fully observable, Deterministic, Static, Discrete, Sequential, Single-agent).
     * Show the **State-space formulation** and mathematical CSP $(X, D, C)$ model with occupancy keys.

### 2. Data Management & Pre-Flight Validation (Input Integrity)
1. Navigate to **Data Management** (`/data`).
2. Click **Load Sample** and select **`tiny`**.
3. **Show Data Tables:**
   * Review the loaded Teachers, Courses, Divisions, Rooms, and Time Grid.
   * Highlight the **Availability Grid** showing faculty availability schedules.
4. **Demonstrate Input Validation:**
   * Click **Validate & Apply Draft**.
   * Note the status banner turns green: `READY • VALIDATED`.
5. **Demonstrate Error Catching (Negative Test):**
   * Go to Courses table, change a teacher ID to `UNKNOWN_TEACHER`.
   * Click **Validate & Apply Draft**.
   * Notice that the validator catches `UNKNOWN_TEACHER`, displays the issue in the issues table, and **blocks generation** until resolved.
   * Revert the change and click **Validate & Apply Draft**.

### 3. Generate Timetable & Live Progress (Search in Action)
1. Navigate to **Generate** (`/generate`).
2. **Review Algorithm Options:**
   * **Config A:** Baseline Backtracking (chronological).
   * **Config B:** Backtracking + MRV/Degree/LCV Heuristics.
   * **Config C:** Forward Checking (FC).
   * **Config D:** Root AC-3 + MAC.
3. Select **Config C** (Forward Checking).
4. Click **Generate Timetable**.
5. **Observe Live Results:**
   * Note the live progress bar and status cards.
   * Inspect the metric cards: Runtime, Build Time, Nodes, Attempts, Backtracks, Consistency Checks, Values Pruned.
   * Click **"Explain this run"** to display transparent, plain-English explanations of how MRV, Degree, LCV, and Forward Checking influenced the search.

### 4. Interactive Timetable Viewer (Solution Quality)
1. Click **"Open in Timetable Viewer"** (or navigate to `/viewer`).
2. **Inspect the Weekly Grid:**
   * Point out that sessions are color-coded by Course.
   * Switch between **Detailed Cards** (shows Teacher, Room, and Course) and **Compact Blocks**.
   * Filter by **Division** (e.g., Division A vs B), **Teacher** (e.g., Dr. Rao), or **Room** (Room 101).
   * Hover over cards to show detailed tooltips with slot times and course descriptions.
3. **Export CSV:**
   * Click **"Download CSV"**.
   * Open the downloaded file to demonstrate the standardized 9-column timetable CSV export.

### 5. Independent Constraint Validation (Certified Proof)
1. Click **"Inspect Constraint Validation"** (or navigate to `/validation`).
2. **Key Talking Points:**
   * Point out the prominent **✔ VALID TIMETABLE** badge.
   * Explain the **Dual Validation Strategy**: The solver uses occupancy keys during search, but this page is generated by an **independent interval-arithmetic validator** completely decoupled from the search engine.
   * Review the **12 Hard Constraint Categories Table**:
     * Notice that every single category (Faculty conflicts, Cohort overlaps, Room collisions, Capacity, Room types, Unavailabilities, Contiguous durations, Day boundaries) is explicitly listed with **0 violations**.

### 6. Infeasibility Proof via AC-3 (Demonstrating Config D Power)
1. Go to **Data Management** (`/data`), load sample **`impossible`**.
2. Click **Validate & Apply Draft**.
3. Go to **Generate** (`/generate`), select **Config D** (Root AC-3 + MAC).
4. Click **Generate Timetable**.
5. **Key Talking Point:**
   * The solver immediately returns **`INFEASIBLE_PROVEN`** with **0 search nodes**!
   * Explain why: Root AC-3 detected that the two sessions of Course X required more usable teacher slots than Teacher T01 had available, causing a domain wipeout during preprocessing before a single search node was expanded.

### 7. Timeouts and Interactive Cancellation (Robustness)
1. Go to **Data Management** (`/data`), select the **Generate tab**.
2. Generate a **Large preset** synthetic instance.
3. Click **Validate & Apply Draft**.
4. Go to **Generate** (`/generate`):
   * Select **Config A** (Baseline).
   * Set **Time Limit** to `2.0` seconds.
   * Click **Generate Timetable**.
   * Observe that the solver halts at 2 seconds and reports **`TIMEOUT`** (honest reporting, never falsely reporting infeasible).
5. Run again with a 30-second limit and click **"Cancel Search"** to demonstrate immediate interactive cancellation.

### 8. Benchmark Matrix & Comparison Page (Empirical Evidence)
1. Navigate to **Comparison** (`/comparison`).
2. Select problem sizes (`small`), algorithms (`A, B, C, D`), and click **Run Benchmark** (or load the saved benchmark file from the dropdown).
3. **Review Aggregate Metrics:**
   * Contrast the attempts between Config A (hundreds of attempts) vs Config B, C, D (minimal attempts due to MRV/LCV).
   * Contrast consistency check overhead (Config D performs hundreds of thousands of checks to maintain arc consistency, whereas Config C achieves the sweet spot with forward checking).
   * Show the four generated report charts in `results/charts/` (`runtime_comparison.png`, `nodes_comparison.png`, `backtracks_comparison.png`, `pruning_comparison.png`).
